# Configure Merge Gates

Generate or update a `.speckit-ci.yml` configuration file that defines the merge gate rules for this project. These rules determine what spec compliance checks must pass before a pull request can be merged.

## User Input

```text
$ARGUMENTS
```

You **MUST** consider the user input before proceeding (if not empty). The user may specify:
- A preset profile (e.g., "strict", "moderate", "relaxed")
- Specific thresholds (e.g., "90% task completion", "require all artifacts")
- Rules to enable or disable (e.g., "skip drift check", "require tests")
- Team size context (e.g., "solo developer", "enterprise team")

## Prerequisites

1. Confirm you are inside a git repository.
2. Check if `.speckit-ci.yml` already exists. If it does, read it and present current configuration before making changes.
3. Check if `.specify/` directory exists to understand which artifacts are available.
4. Check if `.github/workflows/` directory exists to understand existing CI setup.

## Outline

1. **Assess Project Context**: Determine appropriate defaults based on project state.

   - If `.specify/` has spec.md + plan.md + tasks.md → suggest "strict" profile
   - If `.specify/` has only spec.md → suggest "moderate" profile
   - If no `.specify/` directory → suggest "relaxed" profile with artifact creation guidance

2. **Present Gate Profiles**: Show available presets for user selection.

   ```markdown
   ## Available Profiles

   | Profile | Task Completion | Required Artifacts | Drift Check | Test Coverage |
   |---------|----------------|-------------------|-------------|---------------|
   | Strict | 100% | spec + plan + tasks | Required | Required |
   | Moderate | 80% | spec + plan | Optional | Recommended |
   | Relaxed | 50% | spec only | Disabled | Optional |
   | Custom | User-defined | User-defined | User-defined | User-defined |
   ```

3. **Generate Configuration**: Create the `.speckit-ci.yml` file.

   ```yaml
   # Spec Kit CI Guard Configuration
   # Generated by /speckit.ci.gate
   # Docs: https://github.com/Quratulain-bilal/spec-kit-ci-guard

   version: "1.0"

   gates:
     artifacts:
       required:
         - spec.md
         - plan.md
       recommended:
         - tasks.md
         - constitution.md
       fail_on_missing_required: true
       warn_on_missing_recommended: true

     task_completion:
       minimum_percentage: 80
       fail_below_threshold: true
       exclude_phases: []

     drift_detection:
       enabled: true
       fail_on_drift: false
       ignore_patterns:
         - "*.md"
         - "docs/**"

     test_coverage:
       require_test_files: true
       minimum_requirement_coverage: 75
       fail_below_threshold: false

     spec_completeness:
       require_requirements_section: true
       require_success_criteria: true
       require_user_scenarios: false

   reporting:
     format: "markdown"
     post_to_pr: true
     include_badge: true

   branches:
     base: "main"
     protected:
       - "main"
       - "release/*"
   ```

4. **Validate Configuration**: Verify the generated config is valid YAML and all referenced paths exist.

5. **Generate CI Integration Snippet**: Provide a ready-to-use CI workflow snippet.

   ```markdown
   ## GitHub Actions Integration

   Add this step to your workflow:

   \```yaml
   - name: Spec Compliance Check
     run: |
       # Run spec-kit CI guard checks
       specify run speckit.ci.check
   \```
   ```

6. **Summary**: Display the final configuration and next steps.

   ```markdown
   ## Configuration Summary

   | Gate | Setting | Action on Failure |
   |------|---------|-------------------|
   | Required Artifacts | spec.md, plan.md | ❌ Block merge |
   | Task Completion | >= 80% | ❌ Block merge |
   | Drift Detection | Enabled | ⚠️ Warn only |
   | Test Coverage | >= 75% requirement coverage | ⚠️ Warn only |
   | Spec Completeness | Requirements + Success Criteria | ❌ Block merge |
   ```

## Rules

- **Single file output** — all configuration goes into `.speckit-ci.yml` in the project root
- **Non-destructive** — if `.speckit-ci.yml` exists, show diff of proposed changes before overwriting
- **Profile-based** — always offer preset profiles before custom configuration
- **CI-agnostic** — configuration file is tool-agnostic; provide integration snippets for GitHub Actions, GitLab CI, and generic scripts
- **Documented** — include inline YAML comments explaining each setting
- **Sensible defaults** — moderate profile is the default if user doesn't specify
